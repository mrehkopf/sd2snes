# sd2snes USB protocol

DISCLAIMER: This document is an automated analysis of the implemented USB
protocol generated by codex. It might contain inaccuracies but in my opinion
provides a good summary (and unveiled some pretty icky stuff).
Use at your own discretion.

Original text follows. I will make manual edits to this when changes are made
to the protocol.

This document describes the direct USB protocol implemented by this firmware.
It is intended for authors of native clients, device libraries, and bridge
programs. It describes the implementation in this repository at commit
`cf7e21d` (2026-08-15), including implementation quirks that are part of the
observable wire behavior.

This is the low-level binary protocol spoken by the cartridge. It is not the
USB2SNES WebSocket/JSON protocol, although programs such as QUsb2Snes use this
protocol as a device backend.

## Status and important warnings

The protocol has no version negotiation, transaction ID, checksum, or final
write acknowledgement. A client must serialize all transactions and must know
from the request how many bytes to read next.

Several combinations accepted by the parser are unsafe or surprising. In
particular:

- `PUT` to `MSU`, `CONFIG`, or `CFG` is a configuration-register operation,
  not a write to those address spaces.
- File `GET`/`CFG GET` setup errors can leave the firmware waiting in a data
  state. Do not send another command; follow the soft/hard recovery rules
  below.
- Zero-length file/memory `GET`, zero-length ordinary `PUT`, and all-zero
  vector transfers do not complete the state machine. Do not issue them; an
  empty `FILE GET` requires DTR recovery after its size-zero response. The
  special configuration-register paths explicitly described below are the
  exception.
- `STREAM` is experimental, lacks a valid-byte count, and has several flag
  combinations that deadlock or terminate unexpectedly.

These cases are detailed below. A conservative client should initially
implement `INFO`, `GET`, `PUT`, `VGET`, `VPUT`, and the basic filesystem
commands, and keep the advanced flags disabled.

## USB transport and discovery

The device enumerates as a USB 2.0 full-speed CDC ACM serial device:

| Property | Value |
| --- | --- |
| Vendor ID | `0x1209` |
| Product ID | `0x5a22` |
| Device release | `0x0100` |
| Manufacturer | `ikari_01` |
| Product | `sd2snes` |
| Serial | `DEMO00000000` |
| CDC control interface | 0 |
| CDC data interface | 1 |
| Notification endpoint | `0x81`, interrupt IN, 16 bytes |
| Data OUT endpoint | `0x02`, bulk OUT, max packet 64 bytes |
| Data IN endpoint | `0x82`, bulk IN, max packet 64 bytes |

On common operating systems it appears as a serial device such as
`/dev/ttyACM0`. The CDC line coding defaults to 9600 8N1, but the firmware only
stores the setting; it does not determine the USB transfer rate or framing.
Baud rate and parity are therefore immaterial.

The host must assert DTR. The firmware treats CDC `SET_CONTROL_LINE_STATE` bit
0 as the connection state. Deasserting DTR aborts the active top-level protocol
state; asserting it establishes a new connection state. A useful clean-open
sequence is:

1. Open the serial/CDC device in raw binary mode with software and hardware
   flow control disabled.
2. Deassert DTR, clear the host input buffer, and allow the device to observe
   the state change.
3. Assert DTR.
4. Send one request and finish its entire response/data exchange before
   sending the next request.

For a direct USB implementation, DTR is the class/interface control transfer
`bmRequestType=0x21`, `bRequest=0x22`, `wValue=0` or `1`, `wIndex=0`, and
`wLength=0`. The data-interface descriptor contains the invalid string index
`0x5e`, so discovery code should not request or depend on that interface
string.

When using a serial API, ignore USB packet boundaries. A 512-byte application
block is carried as eight 64-byte bulk packets. Adjacent response and data
blocks are chained without an intervening USB short packet. Because the last
logical block is always a multiple of the endpoint size, the firmware emits
one terminating zero-length packet after the entire contiguous IN phase.
Serial APIs normally hide that packet. Always use `read_exact(n)` and
`write_all(n)` loops; a short OS read is not a protocol boundary.

Direct-libusb clients should claim the CDC data interface and reproduce the
DTR control request. There is no USB transfer boundary between the 512-byte
response and following data, or between adjacent data blocks. Read the exact
lengths implied by the application protocol. Depending on host-controller
scheduling, the terminal ZLP may be consumed with the current transfer or a
subsequent read may itself report zero bytes; ignore such a zero-byte
completion and continue waiting for the next expected application block.

## Byte order and terminology

This document uses:

- **request** for the command block sent by the host;
- **response** for the 512-byte status block sent by the device;
- **data block** for file or memory payload;
- **B** for the selected data-block size, either 512 or 64 bytes.

All multibyte request fields, vector addresses, response sizes, and the INFO
firmware identifier use big-endian order unless explicitly noted. Filesystem
directory metadata and INFO bit fields use little-endian order.

Unused request bytes should be zero. Strings are NUL-terminated byte strings.
Filesystem names use the firmware's FatFs code page, Windows-1252 in this
build, rather than UTF-8. A path in the 256-byte argument field can contain at
most 255 non-NUL bytes.

## Framing and transaction model

### Command and data sizes

A normal request is exactly 512 bytes. `VGET` and `VPUT` requests are exactly
64 bytes. The firmware chooses the request length solely from opcode byte 4
after receiving the first 64 bytes.

The payload block size is selected independently:

```text
B = 64    if flags & 0x80
B = 512   otherwise
```

Responses are **always 512 bytes**, even for 64-byte vector requests and when
`B` is 64. The `0x80` flag changes only data blocks. The common vector-command
combination `flags = 0xc0` uses 64-byte data and suppresses the response.

Every outgoing write payload must be padded to a full `B` bytes, including the
last one. Incoming read payload is similarly padded; discard bytes after the
declared logical length. There is no extra application data block when the
length is an exact multiple of `B`. A data-producing request must have a
nonzero logical length: the zero-length paths fail to return the state machine
to idle.

### Transaction shapes

Unless `NORESP` is set, a read operation has this shape:

```text
host    -> request
device  -> 512-byte response
device  -> ceil(logical_size / B) data blocks
```

A write operation has this shape:

```text
host    -> request
device  -> 512-byte response
host    -> ceil(logical_size / B) padded data blocks
          (no completion response)
```

A command without payload is request followed by one response. `NORESP`
removes the response and makes read data begin immediately. Do not infer from
these generic forms that every opcode uses the request size as its logical
payload size; the command descriptions list exceptions.

Only one transaction may be active. Do not pipeline requests, send the next
request while read data is pending, or interleave payload from different
operations. Responses contain no request opcode or sequence number with which
to correlate them.

### Resynchronization

There is no in-band synchronization marker safe for arbitrary payload: the
four-byte magic can also occur in file or memory data. For a hang before any
payload has progressed, such as a deliberately avoided zero-length operation,
a soft abort is:

1. Deassert DTR.
2. Wait briefly for the firmware to leave its current state.
3. Flush unread host input.
4. Assert DTR and begin a new transaction.

Closing and reopening the CDC port usually toggles DTR and has the same
top-level effect. However, this is **not a complete parser reset**. The DTR
handler does not clear a partially accumulated request/data block or the
static byte counters used by an interrupted data phase. Consequently:

- never intentionally abort after sending only part of a 64- or 512-byte
  logical block;
- once a successful payload phase begins, finish it exactly as declared;
- if a timeout, disconnect, or error makes the partial-block/data-counter state
  uncertain, reset/power-cycle the cartridge MCU before reconnecting. A USB bus
  reset alone does not explicitly clear this protocol state in the firmware;
- the `POWER_CYCLE` command is usable only while the parser is still aligned.

Do not try to recover by scanning for or sending another `USBA` block into an
uncertain state. DTR is useful for known state-machine hangs with no byte-count
progress, but an MCU restart is the only reliable recovery from an interrupted
transfer.

## Common request format

Normal requests are laid out as follows:

| Offset | Size | Meaning |
| ---: | ---: | --- |
| `0x000` | 4 | ASCII magic `USBA` |
| `0x004` | 1 | opcode |
| `0x005` | 1 | address space |
| `0x006` | 1 | flags |
| `0x007` | 1 | `LS` metadata flags; zero otherwise |
| `0x008` | varies | opcode-specific auxiliary argument |
| `0x0fc` | 4 | unsigned size, big-endian |
| `0x100` | 4 or 256 | unsigned offset/address, big-endian, or NUL string |

`TIME` uses bytes `0x008` through `0x00f`. `MV` uses a NUL-terminated new name
starting at `0x008`; keep that string, including NUL, entirely before `0x0fc`.

Vector requests replace most of this layout with eight descriptors:

| Offset | Size | Meaning |
| ---: | ---: | --- |
| `0x00` | 4 | ASCII magic `USBA` |
| `0x04` | 1 | `VGET` or `VPUT` |
| `0x05` | 1 | address space |
| `0x06` | 1 | flags |
| `0x07` | 25 | reserved, zero |
| `0x20 + 4*i` | 1 | length of vector `i` |
| `0x21 + 4*i` | 3 | 24-bit address of vector `i`, big-endian |

There are eight vectors. A zero length skips a descriptor; a nonzero length is
1 through 255 bytes. The logical payload is the concatenation of all nonzero
vectors in descriptor order, and its length is the sum of their lengths.
Padding is applied only at the end of that concatenated stream, not after each
vector.

## Opcodes

| Value | Name | Request size | Summary |
| ---: | --- | ---: | --- |
| `0x00` | `GET` | 512 | Read file, memory, config key, or FPGA register |
| `0x01` | `PUT` | 512 | Write file/memory or an FPGA register |
| `0x02` | `VGET` | 64 | Read up to eight memory spans |
| `0x03` | `VPUT` | 64 | Write up to eight memory spans |
| `0x04` | `LS` | 512 | List directory |
| `0x05` | `MKDIR` | 512 | Create directory |
| `0x06` | `RM` | 512 | Remove file or empty directory |
| `0x07` | `MV` | 512 | Rename within the same directory |
| `0x08` | `RESET` | 512 | Pulse/reset the running SNES program |
| `0x09` | `BOOT` | 512 | Load and start a ROM |
| `0x0a` | `POWER_CYCLE` | 512 | Reset the cartridge MCU |
| `0x0b` | `INFO` | 512 | Return firmware and runtime information |
| `0x0c` | `MENU_RESET` | 512 | Return to the cartridge menu |
| `0x0d` | `STREAM` | 512 | Experimental MSU/snapshot stream |
| `0x0e` | `TIME` | 512 | Set RTC |
| `0x0f` | `RESPONSE` | — | Device-to-host response opcode |

An unknown opcode produces error 1. A block with invalid magic is silently
discarded and receives no response.

## Address spaces

| Value | Name | Intended use |
| ---: | --- | --- |
| `0x00` | `FILE` | SD-card filesystem |
| `0x01` | `SNES` | Cartridge PSRAM / captured SNES context |
| `0x02` | `MSU` | MSU data buffer for reads/streaming |
| `0x03` | `CMD` | FPGA command BRAM |
| `0x04` | `CONFIG` | FPGA configuration registers |
| `0x05` | `CFG` | Values from `/sd2snes/config.yml` |

The names are not a uniform read/write contract. See the matrix below.

| Operation | FILE | SNES | MSU | CMD | CONFIG | CFG |
| --- | --- | --- | --- | --- | --- | --- |
| `GET` | whole file | memory | buffer | BRAM | one register byte | config value string |
| `PUT` | whole file | memory | **FPGA register write** | BRAM | FPGA register write | **FPGA register write** |
| `VGET` | rejected | spans | spans | spans | special/avoid | rejected behavior |
| `VPUT` | rejected/unsafe | spans | **register behavior** | spans | special/avoid | special/avoid |

For `SNES`, the transmitted address is 32 bits but hardware uses its low 24
bits. `CMD` and `MSU` accessors use only the low 16 bits.

`SNES` is cartridge-side memory, not a generic live SNES bus read primitive.
Common firmware regions include:

| SNES-space address | Typical contents |
| ---: | --- |
| `0x000000` | loaded ROM image |
| `0xe00000` | save RAM staging area |
| `0xf50000`–`0xf6ffff` | captured WRAM, 128 KiB |
| `0xf70000`–`0xf7ffff` | captured VRAM bytes, 64 KiB |
| `0xf80000`–`0xf8ffff` | APU upload shadow/ports |
| `0xf90000`–`0xf901ff` | captured CGRAM |
| `0xf90200`–`0xf9041f` | captured OAM area |
| `0xf90500`–`0xf906ff` | PPU-register snapshot |
| `0xf90700`–`0xf908ff` | CPU/DMA-register snapshot |
| `0xff0000` and above | menu/firmware communication structures |

The `0xf5xxxx` context regions are write-snooped snapshots maintained by the
FPGA; they are not guaranteed to be atomic or authoritative live state. Their
availability and meaning can vary with the loaded FPGA core. Autotracker-style
WRAM reads conventionally use `0xf50000 + WRAM_offset`.

`CMD` exposes internal command BRAM mapped into the SNES command window and
can trigger firmware or in-game-hook behavior. Treat it as an expert interface,
not general RAM.

## Flags

| Mask | Name | Meaning |
| ---: | --- | --- |
| `0x01` | `SKIPRESET` | `BOOT`: load while leaving reset asserted |
| `0x02` | `ONLYRESET` | `BOOT`: skip loading, only release/handle reset |
| `0x04` | `CLRX` | Clear the in-game execute hook before operation |
| `0x08` | `SETX` | Install/trigger the in-game execute hook afterward |
| `0x10` | `STREAMBURST` | Select burst behavior for `STREAM` |
| `0x20` | — | unused |
| `0x40` | `NORESP` | Suppress the 512-byte response |
| `0x80` | `64BDATA` | Use 64-byte data blocks instead of 512-byte blocks |

Unknown bits are ignored. `SKIPRESET` and `ONLYRESET` matter only to `BOOT`;
`STREAMBURST` matters only to `STREAM`.

`CLRX` and `SETX` are specialized in-game-hook controls. `CLRX` writes an RTS
instruction before the operation. `SETX` copies bytes from the last requested
SNES-space address into executable command BRAM, appends an indirect jump, and
triggers the hook. There is no general bounds validation, and vector commands
refer to the last vector. Do not set either flag in an ordinary client.

`NORESP` is useful only when the client can derive all following lengths and
does not need the setup error. It is commonly combined with `64BDATA` for
vector requests. Never set `NORESP` on `STREAM`: the implementation waits for
an IN-completion event that no initial response creates and can deadlock.

## Response format

Every ordinary response is a 512-byte block:

| Offset | Size | Meaning |
| ---: | ---: | --- |
| `0x000` | 4 | ASCII magic `USBA` |
| `0x004` | 1 | `0x0f` (`RESPONSE`) |
| `0x005` | 1 | error/status byte; zero means initial setup succeeded |
| `0x006` | 246 | normally zero; INFO uses part of this area |
| `0x0fc` | 4 | unsigned result size, big-endian |
| `0x100` | 256 | normally zero; INFO uses part of this area |

The result-size field means:

- requested size for ordinary memory reads/writes;
- actual full file size for `FILE GET`;
- string length including terminating NUL for `CFG GET`;
- sum of vector lengths for `VGET`/`VPUT`;
- fixed value 1 for `LS` (not the listing byte count);
- often merely the echoed request size for commands without data.

It is not a reliable generic indication of how much data follows. Dispatch on
the original opcode/space and the rules in this document.

The response reports only command setup. A successful `PUT` response is sent
before payload is received, and there is no final acknowledgement. Later SD
read/write failures are also not reported to the host.

### Error values

Some file operations expose FatFs `FRESULT` values directly:

| Value | FatFs meaning | Value | FatFs meaning |
| ---: | --- | ---: | --- |
| 0 | OK | 10 | write protected |
| 1 | disk error | 11 | invalid drive |
| 2 | internal error | 12 | volume not enabled |
| 3 | not ready | 13 | no filesystem |
| 4 | file not found | 14 | mkfs aborted |
| 5 | path not found | 15 | timeout |
| 6 | invalid name | 16 | locked |
| 7 | denied | 17 | not enough memory |
| 8 | already exists | 18 | too many open files |
| 9 | invalid object | 19 | invalid parameter |

This is not consistent across opcodes:

- `FILE PUT` returns the initial `f_open` result directly.
- `FILE GET` bitwise-ORs `f_stat` and `f_open` results, so the byte is not
  necessarily one valid enum value.
- `LS`, `MKDIR`, `RM`, and `MV` reduce every failure to 1.
- unsupported/invalid combinations generally return 1.
- a missing `CFG` key reports 1, but also triggers an implementation bug
  described under `GET`.

For a data-producing operation, treat any nonzero response as a reason to
abort. Some error paths nevertheless enter data mode and can otherwise consume
the next command as payload. A DTR cycle is sufficient only when no data-phase
counter could have advanced; use an MCU reset when that is uncertain.

## Command details

### `GET` (`0x00`)

#### `FILE GET`

- Put the NUL-terminated path at `0x100`.
- The request size and offset fields are ignored.
- The firmware stats and opens the file from offset zero.
- The response size is the actual file size.
- Read `ceil(response_size / B)` data blocks and discard final padding.

Prefer absolute paths. If setup returns an error, resynchronize immediately;
the error path can retain stale file-size state and enter a broken data loop.

#### `SNES`, `MSU`, and `CMD GET`

- Put the requested byte length at `0x0fc`.
- Put the start address at `0x100`.
- Read exactly `ceil(length / B)` data blocks after the response.

`SNES` uses the low 24 address bits. `MSU` and `CMD` use the low 16 bits.

#### `CFG GET`

- Put a NUL-terminated configuration key at `0x100`.
- The firmware reads `/sd2snes/config.yml` and returns the raw scalar token as
  a NUL-terminated string.
- The response size includes that terminating NUL.
- Read one or more padded data blocks according to that response size.

Only query keys known to exist. On a missing key, the code copies and measures
an uninitialized token buffer before noticing the miss. This can return stale
data or leave the protocol in an invalid data state. Resynchronize after any
nonzero response.

#### FPGA configuration-register read

Any otherwise-unhandled `GET` space, notably `CONFIG`, performs a one-byte FPGA
register read:

```text
group = request_size & 0xff
index = request_offset & 0xff
```

Exactly one logical data byte is returned, padded to `B`, regardless of the
response size field. The response size remains the original request size and
may therefore be zero or unrelated. Register definitions are FPGA-core
specific.

### `PUT` (`0x01`)

#### `FILE PUT`

- Put the complete byte length at `0x0fc`.
- Put the NUL-terminated destination path at `0x100`.
- The file is created or truncated before the response is sent.
- After a zero-error response, send `ceil(length / B)` full data blocks.
- There is no final response.

Do not send a zero-length `PUT`; the state machine waits for a data block even
though no bytes are required. Likewise, after a successful empty-file `GET`
response (size zero), toggle DTR before the next command because the read state
does not complete. File write errors after the initial open are not reported.

#### `SNES PUT` and `CMD PUT`

- Put the byte length at `0x0fc` and address at `0x100`.
- After the response, send the concatenated bytes padded to full blocks.
- `SNES` uses the low 24 address bits; `CMD` uses the low 16 bits.
- There is no final response.

#### FPGA configuration-register write

Every `PUT` space other than `FILE`, `SNES`, and `CMD` takes this path,
including `MSU`, `CONFIG`, and `CFG`:

```text
group        = request_size   & 0xff
index        = request_offset & 0xff
value        = (request_offset >> 8)  & 0xff
inverse_mask = (request_offset >> 16) & 0xff
```

The operation still waits for one full data block after its response, but the
payload byte is ignored. The register write uses only fields encoded in the
request. This makes `PUT MSU` particularly deceptive: it does **not** write the
MSU read buffer.

### `VGET` (`0x02`) and `VPUT` (`0x03`)

Use the 64-byte vector request format described above. For ordinary `SNES` or
`CMD` access:

- `VGET` returns each span concatenated in vector order;
- `VPUT` consumes the same concatenated layout;
- the response size, if enabled, is the sum of vector lengths;
- there is no padding between spans.

`VGET MSU` uses the MSU read accessor. `VPUT MSU` does not symmetrically write
it; it takes configuration-register behavior.

The conventional flags are `NORESP | 64BDATA` (`0xc0`). With these flags a
64-byte request is followed immediately by 64-byte data blocks in the relevant
direction. A normal response, if requested, remains 512 bytes.

At least one descriptor must have nonzero length. An all-zero vector request
hangs in data state. The implementation also examines one descriptor-sized
slot just beyond the 64-byte request while looking for the end; keeping all
unused bytes in preceding normal requests zero prevents stale data there from
being mistaken for a ninth vector.

Do not use vectors with `FILE`. The implementation rejects them, but `VPUT
FILE` can still transition into a payload state after returning an error. Also
avoid vector `CONFIG`/`CFG`: descriptor length/address fields are repurposed as
register fields, the advertised total is misleading, and write data is
ignored.

### `LS` (`0x04`)

Put the directory path at `0x100`. The space byte is ignored, but use `FILE`.
Byte `0x007` selects optional metadata:

| Mask | Field appended to each entry |
| ---: | --- |
| `0x01` | size, unsigned 32-bit little-endian |
| `0x02` | FAT date, unsigned 16-bit little-endian |
| `0x04` | FAT time, unsigned 16-bit little-endian |
| `0x08` | FatFs attribute byte |

Each entry is encoded in this exact order:

```text
u8 type                       # 0 = directory, 1 = file
[u32le size]                  # if metadata bit 0x01
[u16le FAT date]              # if metadata bit 0x02
[u16le FAT time]              # if metadata bit 0x04
[u8 attributes]               # if metadata bit 0x08
u8 name[]
u8 0                          # NUL terminator
```

Entries are packed into data blocks without splitting an entry across blocks.
The first byte at each expected entry boundary is therefore one of four record
types:

| Byte | Meaning |
| ---: | --- |
| `0x00` | a directory entry follows |
| `0x01` | a file entry follows |
| `0x02` | continuation marker: discard the remainder of this block |
| `0xff` | end marker: discard the remainder and stop reading |

Marker values are meaningful only where the parser expects the next entry's
type byte. The same values can occur normally inside metadata or a filename;
do not scan the block byte-by-byte looking for markers.

#### Exact occurrence of `0x02`

Before emitting an entry, the firmware calculates its complete encoded size:

```text
needed = 1                         # type
       + selected metadata bytes  # 0 through 9
       + name length
       + 1                         # terminating NUL
remaining = B - current_offset
```

If `needed <= remaining`, it emits the complete entry. Equality counts as a
fit: an entry that ends exactly at the block boundary does **not** cause a
marker in that block.

If `needed > remaining`, it emits only `0x02` at `current_offset` and sends the
block. No prefix of the pending entry is emitted. On the next block the
firmware reuses that pending directory entry without calling `f_readdir` again,
so its complete encoding begins at offset zero.

Consequently, `0x02` can occur:

- at offset zero if the pending entry cannot fit in an empty block; or
- immediately after one or more complete entries when the next entry cannot
  fit in the bytes left in the block; or
- in the final byte of a block when exactly one byte remains and the next entry
  needs more than one byte.

Everything after `0x02` belongs to neither the listing nor the next entry. The
firmware does not clear that tail, so it can contain stale bytes from an older
USB buffer. Discard the entire remainder of the block even if it resembles
valid entries.

An entry whose complete encoding is larger than `B` can never make progress:
every new block contains `0x02` at offset zero and retries the same entry. With
512-byte blocks, the configured 255-byte maximum filename and all metadata fit
comfortably. With `64BDATA`, a sufficiently long filename or metadata-bearing
entry causes this infinite continuation loop; this is why clients should use
512-byte blocks for `LS`.

#### Exact occurrence of `0xff`

The firmware emits `0xff` at the current entry boundary when any of these
conditions occurs:

- the initial `f_opendir` failed, making it byte zero of the first data block;
- the next `f_readdir` call fails; or
- `f_readdir` reports the normal end of the directory by returning an empty
  short filename.

Thus `0xff` may appear immediately after the last complete entry in a block.
If that entry ended exactly at the block boundary, there was no opportunity to
test for another entry, so a new block is sent with `0xff` at offset zero. The
current firmware zero-fills the tail after `0xff`, but clients should merely
discard it and must not require zeros.

A volume-label entry is skipped without emitting a record. Entry order is the
filesystem's enumeration order.

A block-oriented parser should behave like this:

```text
repeat:
    block = read_exact(B)
    offset = 0
    while offset < B:
        kind = block[offset]
        if kind == 0x02:
            break                 # discard tail; read another block
        if kind == 0xff:
            return complete      # discard tail; do not read another block
        if kind not in {0x00, 0x01}:
            return malformed

        offset += 1
        parse exactly the metadata selected by request byte 0x007
        find the filename NUL before the end of this block
        deliver the complete entry
```

If parsing a `0x00`/`0x01` record would run beyond the block or its filename
has no NUL before the block ends, the stream is malformed; a conforming device
would have emitted `0x02` instead of a partial record.

The FAT date is `(year - 1980)` in bits 15:9, month in 8:5, day in 4:0. FAT
time is hour in bits 15:11, minute in 10:5, and seconds divided by two in 4:0.
Attribute bits are 0x01 read-only, 0x02 hidden, 0x04 system, 0x08 volume label,
0x10 directory, and 0x20 archive.

Use 512-byte data blocks for listings.

The response size is always 1 and does not predict listing length. Even an
initial directory error enters the listing state and normally emits an end
marker block. A conservative client should resynchronize on a nonzero response
instead of depending on that detail.

### `MKDIR` (`0x05`) and `RM` (`0x06`)

Put the path at `0x100` and use the `FILE` space. `MKDIR` creates one directory.
`RM` unlinks a file or empty directory. Each returns one response and no data.
The error byte is 0 for success or 1 for any FatFs error.

### `MV` (`0x07`)

`MV` renames an item without changing its directory:

- old full path: NUL-terminated string at `0x100`;
- new basename only: NUL-terminated string at `0x008`.

The firmware extracts the directory portion of the old path and appends the
new basename. Include a slash in the old path, preferably by usinog an absolute
path. Without one, the implementation can concatenate the old path and new
name incorrectly. It returns one response with error 0 or 1.

Moving to a different directory is not supported by this command.

### `RESET` (`0x08`) and `MENU_RESET` (`0x0c`)

Both return a normal response before taking effect. `RESET` requests a reset
of the current SNES program. `MENU_RESET` exits/reset-transitions to the
cartridge menu. Their space, size, and offset fields are not meaningful.

### `BOOT` (`0x09`)

Put the ROM path at `0x100`. With no boot flags, the firmware asserts reset,
loads the ROM and associated state, initializes the FPGA, releases reset, and
enters game mode. The response may be delayed until this work completes, so a
client needs a much longer timeout than for a memory transaction.

The response error byte does not reflect the result of the internal ROM-loading
steps.

The flags support a two-phase workflow:

1. `BOOT | SKIPRESET`: load and initialize but leave reset asserted and do not
   enter the game loop.
2. Perform intended patch/memory operations.
3. `BOOT | ONLYRESET` without `SKIPRESET`: skip loading, release reset, and
   enter the game loop.

If both bits are combined, the actual control flow is implementation-specific
and not useful to normal clients.

### `POWER_CYCLE` (`0x0a`)

This queues a response and immediately resets the cartridge MCU. Because USB
transmission is asynchronous, a host may receive only the beginning of the
512-byte response before the device disconnects. Treat USB disconnect and
reenumeration as success; do not require a complete response.

### `INFO` (`0x0b`)

`INFO` has no data phase. It returns a normal 512-byte response with these
additional fields:

| Offset | Size | Byte order | Meaning |
| ---: | ---: | --- | --- |
| `0x006` | 4 | little-endian | active FPGA feature bits (currently low 16 bits used) |
| `0x00a` | 2 | little-endian | system-configuration bits |
| `0x00c` | 4 | — | reserved/zero |
| `0x010` | 240 | bytes | current ROM path, NUL/padded |
| `0x100` | 4 | big-endian | opaque firmware build/version identifier |
| `0x104` | 64 | bytes | firmware version string, NUL/padded |
| `0x144` | 64 | bytes | device name, NUL/padded |

The build identifier comes from the firmware image header and should be
treated as an opaque 32-bit value, not assumed to be a semantic version.

System-configuration bits are:

| Bit | Meaning |
| ---: | --- |
| 0 | in-game hook enabled |
| 1 | save states enabled and the in-game hook is enabled |

Feature bits are the currently active FPGA feature mask:

| Bit | Symbol/meaning |
| ---: | --- |
| 0 | DSPX |
| 1 | ST0010 |
| 2 | S-RTC |
| 3 | MSU1 |
| 4 | feature 213F |
| 5 | command unlock |
| 6 | 2100/context capture |
| 7–10 | encoded 2100 brightness limit, not four independent flags |
| 11 | DMA1 |
| 12 | Satellaview base |
| 13 | combo |
| 14–15 | currently unused |

These describe active configuration, not necessarily every capability the
hardware could load. Very long current-ROM paths are truncated at the end by
the current implementation despite a stray calculation suggesting the author
intended front truncation.

### `TIME` (`0x0e`)

The MCU's internal RTC is programmed with the received time. The expected
format is as follows:

| Offset | Meaning |
| ---: | --- |
| `0x008` | seconds |
| `0x009` | minutes |
| `0x00a` | hour |
| `0x00b` | day |
| `0x00c` | month, 1–12 |
| `0x00d` | year high byte |
| `0x00e` | year low byte |
| `0x00f` | weekday (the RTC routine recalculates it) |

### `STREAM` (`0x0d`) — experimental

Only the `MSU` space is intended. The request size and offset do not provide a
reliable finite byte count. Do not set `NORESP`.

Non-burst mode continues until DTR is deasserted. Every eighth block is filled
from the captured SNES context beginning at `0xf50000`; other blocks contain up
to 64 bytes from the live MSU queue. Unused bytes are `0xff`. Even when `B` is
512, no more than 64 meaningful bytes are placed in each block.

Burst mode (`STREAMBURST`) emits MSU chunks until an underrun, then pads the
last block with `0xff` and stops. Its read pointer persists between burst
requests. With 512-byte blocks, every at-most-64-byte chunk appears short and
the stream ends after one block, so burst mode requires `64BDATA` for useful
operation.

There is no valid-byte count, and genuine `0xff` data is indistinguishable from
padding. A wrong space still enters stream state. This operation is therefore
unsuitable as a robust general-purpose transfer API.

## Minimal client example

The following Python sketch uses pyserial and shows the framing rules for INFO
and a SNES-space read. Production code should add device discovery, reasonable
operation-specific timeouts, DTR recovery, and explicit error types.

```python
import struct
import time
import serial

MAGIC = b"USBA"
RESPONSE = 0x0F

GET = 0x00
INFO = 0x0B
SNES = 0x01


def write_all(port, data):
    view = memoryview(data)
    while view:
        written = port.write(view)
        if not written:
            raise TimeoutError("short USB write")
        view = view[written:]


def read_exact(port, count):
    result = bytearray()
    while len(result) < count:
        chunk = port.read(count - len(result))
        if not chunk:
            raise TimeoutError(f"wanted {count}, got {len(result)} bytes")
        result.extend(chunk)
    return bytes(result)


def request(opcode, space=0, flags=0, size=0, address=0):
    block = bytearray(512)
    block[0:4] = MAGIC
    block[4] = opcode
    block[5] = space
    block[6] = flags
    struct.pack_into(">I", block, 0xFC, size)
    struct.pack_into(">I", block, 0x100, address)
    return block


def read_response(port):
    block = read_exact(port, 512)
    if block[0:4] != MAGIC or block[4] != RESPONSE:
        raise ValueError("lost protocol synchronization")
    error = block[5]
    size = struct.unpack_from(">I", block, 0xFC)[0]
    return block, error, size


with serial.Serial("/dev/ttyACM0", timeout=2, write_timeout=2) as port:
    port.dtr = False
    port.reset_input_buffer()
    time.sleep(0.05)
    port.dtr = True

    # INFO: all fields other than the common header are zero in the request.
    write_all(port, request(INFO))
    info, error, _ = read_response(port)
    if error:
        raise RuntimeError(f"INFO failed: {error}")
    features = struct.unpack_from("<I", info, 0x06)[0]
    version = info[0x104:0x144].split(b"\0", 1)[0].decode("ascii", "replace")
    device = info[0x144:0x184].split(b"\0", 1)[0].decode("ascii", "replace")
    print(hex(features), version, device)

    # Read 1000 captured-WRAM bytes. Default B is 512.
    logical_size = 1000
    write_all(port, request(GET, SNES, size=logical_size,
                            address=0xF50000))
    _, error, returned_size = read_response(port)
    if error:
        raise RuntimeError(f"GET failed: {error}; reset DTR before continuing")
    if returned_size != logical_size:
        raise ValueError("unexpected GET size")
    padded_size = ((logical_size + 511) // 512) * 512
    data = read_exact(port, padded_size)[:logical_size]
```

For a path-taking request, replace the four-byte address at `0x100` with the
encoded path plus a NUL. Validate that it fits before assigning it to the
packet. For `VGET`/`VPUT`, construct a 64-byte request and place descriptors at
`0x20`.

## Client implementation checklist

- Discover by VID/PID and verify response magic/opcode; do not rely on the
  placeholder serial string being unique.
- Assert DTR and provide both a soft DTR abort and a documented hard-reset path
  for interrupted transfers.
- Serialize transactions with one connection-wide lock.
- Zero-initialize requests and NUL-terminate every string in its field.
- Encode request size/address and vector addresses big-endian.
- Always read a 512-byte response unless `NORESP` is set or a reset disconnects
  the device.
- Treat `64BDATA` as a payload-only setting.
- Pad every host-to-device payload to a full 64- or 512-byte block.
- Read and discard device padding based on the command's actual logical size.
- Give `BOOT` and filesystem commands longer timeouts than memory operations.
- Resynchronize on an error from a data-producing command.
- Do not use zero-length data operations, vector `FILE`, `PUT MSU`, or
  unsafe `STREAM` flag combinations.
- Decode filenames as CP1252 unless a future firmware build changes FatFs
  configuration.
